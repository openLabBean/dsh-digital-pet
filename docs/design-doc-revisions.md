# 设计方案修订建议（v1.0 → v1.1 合并清单）

对象：`~/Documents/Program/whalecloud/docs/deepseek-pet-development-design-v1.md`（未直接改动该文件，等你确认后合并）。

依据：本次在 DSH（Desktop 应用内 Web GUI，1280×800；ui-test 实例 + 用户 desktop profile 热加载）上的实测实现与 144 例测试。逐条给出「原文 → 建议改法 → 实测依据」。

## 1. §1 首发数量行（必改，事实性错误）

原文（第 15 行）：
> `| 首发数量 | 需求写“6 款”，清单有 86 款；按前六款首发，牛牛和山羊预留扩展，数据模型支持全部6款 |`

问题：「清单有 86 款」是笔误（素材清单是 8 款：鲸/猴/鸭/鸡/猫/狗/牛/山羊）；同句内部也自相矛盾（前六 + 牛 + 山羊 = 8）。且「数据模型支持全部6款」应为 8 款。

建议改为：
> `| 首发数量 | 需求写“6 款”，现成素材 8 款；按前六款（鲸鱼/猴子/鸭子/小鸡/猫/狗）首发，牛牛、山羊素材已完成、作为 v1.1 扩展开放，数据模型支持全部 8 款 |`

## 2. §2 素材段（必改，实测口径）

原文（第 47 行）：
> `工作区已有 output/imagegen/pet-family-v2/ 八款静态参考：六阶段、便便与纪念形象、六项护理动作。它们可以用于角色方向确认，尚不能直接作为可发布的动画包；需完成切图、透明边缘、统一锚点和逐帧动画。`

实测：切图、透明边缘、统一锚点**已经完成**——8 物种 × 14 slot = 112 张精灵 + 8 张校验图，统一高 96px、RGBA 紧裁、`slice.py --verify` 通过，已能直接驱动 UI。唯一未完成的是逐帧动画（每张是静态单帧）。

建议改为：
> `工作区已有 output/imagegen/pet-family-v2/ 八款静态参考，并已切分为 8 物种 × 14 slot 的可直接使用精灵（`plugins/dsh-digital-pet/assets/sprites/`，统一 96px 高、紧裁透明、manifest + 校验脚本）。它们是单帧静态图，可驱动"按年龄/动作切换形象"的 v1 表现；逐帧动画（呼吸/眨眼/走路）仍需新的序列帧资产。`

## 4. §13 动画规格（口径修正）

原文要求「每物种×六年龄至少 12 组动画、首发 6×6×12=432 组」。实测口径应拆成两层：
- **形象覆盖**：v1 已达成 8×6 = 48 个年龄形象（+6 个动作/状态图），按年龄切换即可"看得出长大"。
- **逐帧动画**：0 组。要按 §13 落地需 432 组序列帧，且每帧成本远高于静态切图；建议 v1.1 的先决条件是先做 1 个物种（鲸鱼）× 6 年龄的 12 组动画做成本与观感验证，再决定是否铺开。

## 5. §12 / §10 的实现期补充（新增事实）

1. **存档按 profile 隔离**（强化 §1「每个本地 Harness profile 一只」）：`<profileDir>/dsh-digital-pet/pet-state.json`；`DSH_PET_DATA_FILE` 可覆盖，用于测试/演示；旧全局存档首次启动自动迁移。
2. **Token 记账去重键**：`${session.id}:${event.seq}`（响应级），与 §9.1「provider + response_key」等价落地；historical replay（无 seq）不发币。
3. **离线**：需 Host 显式传 `offline` 标志（进程退出无法仅靠时间推断），≤24h 保护下限 30/40/30/40、>24h 自动托管 ≥60，与 §10.2 一致。
4. **排泄**：实现为"每本地日 ≤1 份、并发 ≤2"，替代 §6.2「滚动 24 小时」的严格表述（更易解释，且不随点击次数膨胀）。
5. **零食**：按 2 半份入库且不可拆；主食可半份（§9.2 的等价拆分只适用于主食）。
6. **睡眠中动作**：允许开始，洗澡的唤醒由 UI 负责（§7.3 的"睡眠中需先主动唤醒"落在客户端）。
7. **托管**：用户主动开启托管会取消在途动作并释放预留（§10.2 未定义，建议补一句）。
8. **请求幂等**：v1 未实现 requestId 幂等键；写操作依赖前置条件（库存/余额/冷却）阻断重复，读操作天然幂等。若后续要多窗口严格幂等，建议在 §12.3 明确 requestId 表。

## 6. 数值模拟结论（`tools/simulate.mjs` / `docs/balance-report.md`，181 天 × 9 策略）

| 设计问题 | 模拟结论 | 建议 |
|---|---|---|
| 每天 1 顿整份够不够 | 够，但仅 11% 余量（日 H 流失 54 vs +60，最低 H 44） | 维持；若想更舒适可把基础口粮半份价格从 6 调到 5 |
| 无 Token 用户会不会饿死 | 不会，且与花金币完全等价（免费救济 60H/24h ≈ 流失的 111%） | 把 `FOOD_CATALOG.relief.effectsPerWhole.H` 60→36~42，或领取冷却 24h→36h；引擎没有饿死路径，所以降低不会致死只会降低"喂饱"的满足感 |
| 每日 100 金币上限是否合理 | 严重过剩（有用支出仅 12 币/天，8.3×） | `ECONOMY_RULES.dailyCoinCap` 100→20~30，或增加高价装饰/玩具消耗 |
| 离线（周末/出差）会不会被惩罚 | 不会，≥24h 自动托管托底 60，反而比每天在线更舒服；24h 分界处有 30↔60 的悬崖 | 建议把托管托底下调到 45~50，或让 >7 天离线只托底 40，减少"越久不管越健康"的逆向激励 |
| 亲密度/体力机制 | 亲密度约 20 天刷满（日上限 5、总上限 100），之后 5 个月无反馈；体力每晚 +60/夜远大于清醒 -24/天，自动休息几乎不触发 | 亲密度上限提到 300 或加阶段解锁；体力改为睡眠恢复按缺失量比例（如 +40%） |

说明：以上为确定性引擎的离线模拟，不是真人数据；V1 不改常数以与设计稿保持一致，待 v1.1 决策。

## 9. 送养（第 7 轮反馈，v1 已实现）

设计稿 §3 写「首版不提供随手释放或强制换宠，避免误删和重复刷赠礼」。用户在实际试用后要求在设置页最下方提供「送进宠物救助站」。v1 的处理：

| 设计稿 | v1 实际 | 说明 |
|---|---|---|
| 不提供释放/换宠 | 提供**显式送养**（两步确认），但仍是「删除当前宠物 → 重新领养」，不是多宠切换 | 满足用户需求，同时用红字确认 + 说明文案降低误删风险 |
| 送养需独立确认和永久记录 | 两步确认已实现；**未做永久记录**（不写纪念册） | 用户要求「删除宠物数据」；若后续需要审计，可加 `surrenderedPets` 表 |
| 换宠不能重复刷首赠 | `profile.firstGiftGranted` 不会被送养重置 | 送养后重领金币不变，实测通过 |

## 10. 照顾操作精简为 5 项（第 8 轮反馈，v1 已实现）

设计稿 §6.3 / §7.3 / §13 定义了六项照顾操作，其中「梳理（grooming，按物种显示为梳毛 / 皮肤刷洗 / 羽毛护理）」在 v1 UI 中被移除：

| 设计稿 | v1 实际 | 说明 |
|---|---|---|
| 六项照顾操作（含梳理、喂水） | UI 只提供 **4 项**（喂食/逛街/洗澡/铲屎） | 用户反馈「皮肤刷洗按钮操作去掉」「喂水操作按钮去掉」；引擎、接口、素材保留，未来可恢复入口 |
| 每 72h 出现梳理诉求 | 引擎仍会产出该诉求，但客户端不展示 | 避免出现没有可用按钮的提示 |
| §5 清洁恢复依赖洗澡 + 梳理 | 现在只靠洗澡（+60）与铲屎（不影响 C） | 清洁每 2–3 天洗澡一次即可维持，长期模拟（`tools/simulate.mjs`）结论不变 |

## 13. 待机动效（第 11 轮）

设计稿 §4.1/§13 只要求「生命在于运动」的表现，未规定待机频率。实现取舍：

- 醒着 4.8s 一个呼吸周期（约 12 次/分），睡眠 6.4s（更慢更浅），饥饿 4.6s 轻微摇晃；幅度控制在 2–3 逻辑像素 + ≤2% 缩放，不干扰阅读与点击。
- 设置页大图与桌面悬浮宠物同源同参数，避免「大图动、桌面不动」的不一致。
- 遵循系统「减弱动态效果」：开启后两处静止（A20 无障碍要求优先于表现）。

## 14. 物种名与英文名展示（第 12 轮）

设计稿 §2 的表头是「宠物 / 中文名 / 英文名」（牛牛 / 奶糖 / Toffee）。实现口径：

- 领养卡第一行＝物种中文名（鲸鱼、猴子、鸭子、小鸡、猫、狗、牛牛、山羊），第二行＝「角色中文名 · 英文名」；
- 扩展物种（牛牛、山羊）的可见文案与其余六款同构（不加 v1.1 字样），未开放状态只用灰显 + 悬停提示 + `aria-disabled` 表达；
- `cow` 的物种中文名从「牛」统一为「牛牛」，与设计稿一致（数据层 `speciesZh`）。

## 15. 设置页信息架构（第 14 轮）

设计稿 §3 的「偏好设置」区包含显示开关、大小、位置、免打扰等。实际交互中，「桌面显示」是最高频开关，因此上移到页面标题右侧常驻（与标题同一行），其余低频项留在偏好设置卡。行为与数据接口不变（`POST /settings {visible}`）。

## 16. 悬浮层交互简化（第 16 轮）

设计稿 §7.1 原写「悬停展示昵称、阶段、四条小状态条；点击宠物播放一次轻反馈」。实际实现调整为：

- 桌面悬浮层不再展开数值面板（避免小窗长期遮挡工作区），点击 = 抚摸反馈（爱心 + 心情奖励）；
- 状态与数值只在设置页仪表盘查看；桌面保留诉求气泡（可直接点击照顾）、动作倒计时、错误提示与便便配件。

## 17. 成长记录不展示寿终日期与剩余寿命（第 17 轮）

设计稿 §4.1/§7 的「剩余寿命/寿终日期」属于内部计时信息。为避免把「离世倒计时」做成常驻展示、增加陪伴焦虑，界面层调整为：

- 成长记录只展示：物种、出生日期、当前阶段与第几天、距下一阶段、亲密度、主动照顾次数；
- 寿终日期与剩余寿命不在 UI 出现（规则与结算不变，纪念册仍在寿终后生成）。

## 18. 成长记录去掉阶段进度条与六阶段说明（第 18 轮）

设计稿 §7 原设想用进度条 + 六阶段说明表达成长节奏。实际界面简化为纯字段列表（物种/出生日期/当前阶段/距下一阶段/亲密度/主动照顾次数）：

- 进度条在「距离下一阶段」已有文字表达时属冗余装饰，删除以降低视觉噪声；
- 六阶段总览说明只在产品文档与「领养说明」里保留，设置页不再常驻。

## 19. 九款物种全部开放 + 新增恐龙（第 19 轮）

- 设计稿 §1 的「首发六款 + 牛/山羊 v1.1 扩展」已过时：现 **9 款全部开放**（鲸鱼、猴子、鸭子、小鸡、猫、狗、牛牛、山羊、恐龙迪诺），领取入口无灰显。
- 新增物种只需补素材 + 在 Host `SPECIES` 加一行配置；动画复用统一 `data-mood` 机制，无需为每个物种写动画代码。
- 新增一个物种的素材成本参考：1 张 4×4 整图 → `prep_dinosaur.py` 切格/拆便便 → `optimize_sprites.py` 导出，约 135 张精灵中新增 15 张（14 slot + 1 核对图）。

## 20. 恐龙形象清晰度增强（第 20 轮）

- 设计稿 §2「视觉建议」只写了「圆团轮廓、克制表情」，没有规定**素材分辨率与 DPR 的关系**。实测问题：低对比平滑插画在 DPR2 屏幕上按 72 CSS px 显示时，144 设备像素 > 原生 137px，属放大采样，观感发糊。
- 结论（建议写进素材规格）：**单槽精灵的短边应 ≥ 2× 最大显示尺寸的 CSS px**（即 ≥ 144px），否则高 DPR 屏幕上必然被放大。恐龙现在 2× 输出（短边 274–520px），满足该约束。
- 另一个可复用做法：源图若为低对比平滑插画，除超采样外再加「锐化 1.4/220 + 对比 1.08 + 饱和 1.06 + 硬 alpha」，显著改善小尺寸观感；配置化在 `manifest.species[].enhance`，不影响其它物种。

## 20.1 素材版本与缓存（实现细节，供设计稿 §13 补充）

- 精灵接口带 `immutable` 缓存，因此素材必须**可版本化**：`/state` 下发 `assetsVersion`，客户端 URL 追加 `?v=`。设计稿 §13「资源目录与清单」建议补一句：*清单文件变更即视为素材版本变更，客户端必须用版本号破缓存*。
- 恐龙（以及未来任何低对比平滑插画）在 DPR2 屏幕下需求：**短边 ≥ 2× 显示 CSS px**（72px 显示 → ≥144px；考虑 DPR2 即 288 设备像素更稳），本次恐龙用 2× 超采样满足。

## 21. 金币图标（第 21 轮）

- 设计稿 §9「金币」只写了经济数值，没有规定图标。实现上不要用 emoji（`🪙` 在 macOS 渲染偏银色，与「金币」语义不符），改用内联 SVG 金色硬币（外环/内环/高光/¥ 符号），固定色值以保证浅色与深色主题下都是金色。

## 22. Token→金币 的可感知性（第 22 轮）

- 设计稿 §9.1 已要求「界面明确显示今日兑换进度、已获金币和上限」，但 V1 实现漏了这块，导致用户重 token 使用量下只看到钱包不动、误以为逻辑坏了。已补「金币明细」卡。
- 设计建议补充：每日 100 金币上限在重度用户（本机实测单日 3.5 亿 Token ≈ 35 万金币）下会「一早已封顶」，属于**设计如此**；若希望重度使用更有正反馈，可考虑（a）提高上限、（b）超额部分降速兑换（如 10,000:1 不计上限）、（c）超额转成非金币奖励（皮肤/家具）。这是产品决策，V1 保持 100 不变。

## 23. 桌面宠物右键菜单（第 23 轮）

- 设计稿 §7.1 只写了「拖动、短点击、悬停」，没提右键；V1 补充了最小右键菜单：仅一项 `隐藏「昵称」`。
- 与设置页「桌面显示」开关共用同一份 `settings.visible`，没有第二套状态；因此隐藏后从设置页页头一键恢复。
- 后续可扩展为多项目菜单（隐藏 / 打开完整面板 / 托管 / 偏好设置），当前按需求只做隐藏，避免误操作面扩大。

## 24. 睡觉状态的可视符号（第 24 轮）

- 设计稿 §7.1 只规定「宠物睡觉」时用睡眠形象；V1 曾用「💤 睡觉中」文字 chip，后来按反馈删掉。本轮按 6/28 的反馈改为**头顶 ZZZ 符号、不加文字**（桌面悬浮宠物 + 设置页大图两处一致）。
- 符号跟随 `prefers-reduced-motion`：动画关闭但符号保留，避免只靠动画表达状态。

## 25. 金币兑换比例 1,000 → 1,000,000（第 25 轮）

- 设计稿 §9.1 原为「每 1,000 有效 Token = 1 金币，每日封顶 100」。按用户 10-29 指示改为 **每 1,000,000 有效 Token = 1 金币**，每日封顶 100 暂不变。
- 影响换算（按本机实测数据）：
  - 修复前单日 3.5 亿 Token ≈ 35 万金币，00:52 即封顶；改后同样量 ≈ 353 金币，仍会触顶（100 币 = 1 亿 Token/天）。
  - 普通强度（如单日 1,650 万 Token）改后约 16 金币/天，与「每天一餐整份 12 金币」的支出大致匹配，经济更接近设计稿的轻养成定位。
  - 轻度用户（单日 100 万 Token 以内）基本靠每日救济口粮即可维持，金币作为额外乐趣，符合 §1「无 Token 也能养」。
- 同日调整比例的兼容处理：已发金币不回退、不重复补发（见实现报告 §4.26）；记账日仍按 profile 时区 0 点切换。
- 若后续想让重度使用更有正反馈，可选：提高每日封顶 / 超额降速兑换 / 超额转非金币奖励（此前的 A/B/C/D 选项仍然成立）。
## 26. 睡觉表现与「睡眠时间」设置（第 26 轮）

- 设计稿 §5/§13 只写了「宠物睡觉」是独立状态，没有规定睡觉形象。V1 落地为：**独立闭眼精灵（9 物种 × 6 阶段）+ 头顶 ZZZ 符号 + 轻微蜷起呼吸**；其它状态（清醒/饥饿/口渴/动作）保持原样，不因睡觉改造而改变。
- ZZZ 之后若还要更强的表达，可再加「睡梦中飘泡泡」等，需另出素材；当前只用闭眼 + ZZZ，避免过度设计。
- 「睡眠时间」设置从「两个原生 time 输入 + 保存按钮」改为 **24 小时制文本输入 + 改动即保存 + 人类可读窗口提示**。原因：浏览器原生 time 控件在部分区域显示 12 小时制（`12:00 AM/PM`），用户把中午设成午夜后界面仍显示 12:00，排查成本高。设计稿 §5 的「允许用户设置连续 8 小时睡眠窗口」不变，只改输入与提示形式。
- 设计稿 §5 的默认作息仍是 23:00–07:00（8 小时）；本轮不改变默认值。

## 28. 中英双语与语言切换（第 31 轮）

- 设计稿原 §3 只定义了中文界面；插件现在默认中文，可在「设置 → 电子宠物」底部切换 English，写入 profile 存档（`settings.locale`）后立即生效。
- 覆盖范围：插件设置页全部卡片、桌面悬浮层（诉求气泡、操作盘、右键菜单、倒计时、ZZZ 朗读）、领养页、错误提示、金币明细；DSH 宿主自身导航仍跟随宿主语言。
- 词典共 167 个 key，新增文案时中英同步维护；后续接入宿主 locale 服务可直接替换 `setUiLocale` 的来源。
